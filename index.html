Threading Model Comparison

Side-by-side analysis of the three major multithreading models

Many-to-One (M:1)

Limited Parallelism

Multiple user-level threads are mapped to a single kernel thread. The thread library manages scheduling entirely in user space.

Parallelism❌ None (1 CPU at a time)
Overhead✅ Very low
I/O Blocking❌ Blocks all threads
Portability✅ High
Kernel Threads1 per process
ExamplesGreen threads, early JVM
UT1 ─┐
UT2 ─┤→ KT1 → CPU
UT3 ─┘

One-to-One (1:1)

True Parallelism

Each user-level thread is mapped to its own kernel thread. The OS scheduler handles all thread scheduling directly.

Parallelism✅ True (multi-CPU)
Overhead⚠ Higher (kernel threads)
I/O Blocking✅ Only affects 1 thread
Portability⚠ OS-dependent
Kernel Threads1 per user thread
ExamplesLinux pthreads, Windows threads
UT1 → KT1 → CPU1
UT2 → KT2 → CPU2
UT3 → KT3 → CPU3

Many-to-Many (M:N)

Best Balance

Many user-level threads are multiplexed onto a smaller or equal number of kernel threads. Offers flexibility and performance.

Parallelism✅ Yes (bounded)
Overhead✅ Balanced
I/O Blocking✅ Minimal impact
Portability✅ Good
Kernel ThreadsPool (fewer than UTs)
ExamplesSolaris, Go goroutines
UT1 ─┐
UT2 ─┤→ KT1 → CPU1
UT3 ─┤→ KT2 → CPU2
UT4 ─┘
Scheduling Algorithm Comparison

Round Robin (RR)

Each thread gets a fixed time quantum. After quantum expires, thread is preempted and next in queue runs. Fair, prevents starvation, good for interactive systems.

Priority Scheduling

Higher priority threads run first. Can cause starvation of low-priority threads. Used in real-time systems where critical tasks must run immediately.

FCFS (First-Come-First-Served)

Threads run to completion in arrival order. Simple but can cause convoy effect where short jobs wait behind long ones. Non-preemptive.

Semaphore vs Monitor

Semaphore

A synchronization primitive with an integer counter. Two atomic operations: wait() decrements and blocks if zero; signal() increments and wakes a waiter.

  • Binary semaphore = mutex (0 or 1)
  • Counting semaphore = resource pool
  • Low-level, error-prone
  • Must be used carefully to avoid deadlock

Monitor

High-level synchronization construct. Encapsulates shared data with mutually exclusive access. Only one thread can be inside a monitor at a time. Condition variables allow threads to wait inside.

  • Automatic mutual exclusion on entry
  • Condition variables: wait(), signal(), broadcast()
  • Higher-level, less error-prone than semaphores
  • Java synchronized blocks are monitors
OS Concepts Reference

Thread Lifecycle States

RUNNING
Thread is actively executing on CPU
READY
Waiting in queue for CPU allocation
WAITING
Waiting for I/O or event completion
BLOCKED
Blocked on resource or lock
TERMINATED
Execution complete, resources freed

Transition Diagram

NEW → READY (admit)
READY → RUNNING (scheduler dispatch)
RUNNING → READY (preemption / quantum expired)
RUNNING → WAITING (I/O request, semaphore wait)
WAITING → READY (I/O complete, signal received)
RUNNING → TERMINATED (execution complete)

Classic Synchronization Problems

Producer-Consumer

Producer generates items into a bounded buffer; Consumer removes them. Problems: producer adding to full buffer, consumer removing from empty buffer. Solved with: mutex + empty + full semaphores.

Dining Philosophers

5 philosophers alternately think and eat. Must acquire 2 forks to eat. Naive solution causes deadlock. Solution: asymmetric fork ordering (last philosopher picks right first) or using a monitor.

About This Simulator

ThreadOS is a pure JavaScript, browser-based OS threading simulator. All logic runs in the main thread using setInterval for tick-based simulation. No backend required. Modules: simulationEngine.js (core loop), synchronization.js (semaphore/monitor/scenarios), visualization.js (Chart.js + DOM), uiController.js (event handling & wiring).
